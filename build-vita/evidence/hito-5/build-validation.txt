Hardware finding: the normal probe crashed natively on the first physical attempt, on every launch,
with no boot.log record past "PASS logger" - confirmed as a genuine crash (not a controlled FAIL)
by two recovered psp2core-*.psp2dmp core dumps. Both dumps decode to the identical crash: an
"Undefined instruction exception" on the main thread at the same offset relative to the ELF's load
base in both dumps (deterministic - the load base itself shifts slightly between launches, but
PC - base and LR - base do not), with r3 and r12 both holding the 0xdeadbeef poison pattern and PC
landing inside an unrelated global (Settings::values) rather than any real function - executing
through a garbage function pointer, not corruption from this milestone's actual rendering logic.
SwRenderer::RasterizerSoftware is the only place in this whole build that constructs a
Common::ThreadWorker (std::jthread + std::stop_token), and this is the first Vita milestone to
construct one at all; VitaSDK's C++20 standard library does not support this on real hardware, even
though it compiles, links, and (per the earlier commits in this milestone) had already been verified
cross-compiling cleanly for ARMv7 - the gap only showed up under physical testing. Fixed by never
constructing a real std::jthread under AZAHAR_VITA (num_sw_threads = 0, an empty
std::vector<std::jthread> that never instantiates std::jthread's own constructor) and running each
scanline directly on the calling thread instead of through QueueWork/WaitForRequests - correct
either way, since scanlines have no cross-scanline dependencies, and confirmed byte-for-byte
unchanged on the desktop reference (same seven signatures, same two PPM hashes, before and after).
The corrected build then passed three consecutive launches with all seven corpus signatures and
both PPM captures matching the desktop reference exactly, and stable user_free before and after.
